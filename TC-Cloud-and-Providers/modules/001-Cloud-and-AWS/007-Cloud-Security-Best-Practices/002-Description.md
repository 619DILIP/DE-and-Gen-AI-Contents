## Building on the Shared Responsibility Model

The shared responsibility model, introduced earlier in this section, establishes that AWS secures the underlying cloud infrastructure, while the customer is responsible for securing what they configure and build within it. This module covers practical steps that fall on the customer side of that divide, applying directly to the services already covered: EC2, S3, RDS, and IAM.

---

## Securing Compute: EC2

- Restrict security group rules to only the specific ports and IP ranges actually needed, rather than leaving broad access open by default.
- Keep the operating system and installed software on an instance up to date with security patches.
- Avoid storing sensitive credentials directly on an instance, using IAM roles instead, as covered in the previous module.

---

## Securing Storage: S3

- Keep buckets private by default, and only make specific objects public when there is a clear, deliberate need to do so.
- Enable encryption for stored objects, so that data remains protected even if storage access controls were somehow bypassed.
- Enable versioning on important buckets, which keeps previous versions of an object available and provides protection against accidental deletion or overwriting.

---

## Securing Databases: RDS

- Restrict network access to a database so that it can only be reached from specific trusted sources, such as an application server, rather than from the public internet.
- Enable automated backups, covered earlier, which also serve a security purpose by allowing recovery from accidental or malicious data loss.
- Use strong, unique credentials for database access, and rotate them periodically.

---

## Encryption at Rest and in Transit

Two related but distinct concepts appear throughout cloud security:

- **Encryption at rest** protects data while it is stored, for example on an S3 object or an RDS database volume, so that the underlying data cannot be read even if the physical storage were somehow accessed directly.
- **Encryption in transit** protects data while it moves across a network, for example between an application and a database, so that the data cannot be intercepted and read as it travels.

Most AWS services support enabling both forms of encryption, and doing so is considered standard practice rather than an advanced or optional configuration.

---

## Logging and Monitoring

Security is not only about preventing problems, but also about being able to detect and respond to them quickly if they occur. AWS provides logging services that record activity across an account, such as who accessed a particular S3 bucket or made a change to an EC2 security group. Reviewing these logs, or setting up automated alerts based on them, allows unusual or unauthorized activity to be identified quickly, rather than going unnoticed.

---

## Multi Factor Authentication

Multi factor authentication, commonly known as MFA, requires a second form of verification beyond just a password when accessing an AWS account, such as a code generated by an authenticator app. Enabling MFA, particularly for accounts with significant permissions, significantly reduces the risk of unauthorized access even if a password is compromised, and is widely considered one of the single most effective, low effort security practices available.
